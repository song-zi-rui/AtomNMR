# 组内服务器部署与持续标注

按Linux Ubuntu/Debian、能够SSH登录准备；如果组内是Windows或作业调度集群，安装和后台托管部分需要调整。本地电脑不需要保持开机。本文没有连接或操作真实组内服务器。

## 1．运行架构

服务器运行本标注程序、保存SQLite数据库，通过网络调用组内推理API。模型推理在API服务上，因此标注程序本身不需要CUDA、模型权重或训练GPU。

建议起步资源：2–4个CPU核、8GB内存、至少80–100GB本地磁盘空间；这包含约12.55GB主库、迁移暂存和备份余量，是部署建议而非性能保证。SQLite数据库放在服务器本地磁盘，不要让多个机器同时打开同一份NFS/网盘文件。

网页只监听127.0.0.1，通过SSH隧道访问。当前程序没有公网登录认证，因此不要直接改成0.0.0.0后暴露8767端口。

## 2．上传哪些东西

推荐使用生成的代码包 `deploy/atomnmr-server-code-20261031.zip`，它包括：

- `annotation_tool_v3/`：网页、服务器、自动标注、数据库与导出功能，以及公开CA证书。
- `tools/`：原子编号、来源检查等辅助代码。
- `atompeak_data/`、`dict/`、`nmrpeak/utils/vocab_rules.py`：训练包导出依赖。
- `deploy/server/`：CPU环境依赖、服务器入口配置、systemd模板。
- 本说明和代码文件SHA256清单。

代码包不含数据库、API密钥、环境文件、旧备份、模型权重和Python虚拟环境。

另外必须迁移：

1. `data/assignment_database_v1/databases/assignments.sqlite` 的一致性快照：分子、谱、人工/原库/AI标签。
2. 同批次 `ai_annotations.sqlite` 快照：保留任务、历史响应和用量。
3. 同批次 `ai_benchmarks.sqlite` 快照：保留模型对比实验。

最简单的迁移方法：暂停本机自动任务、等请求收尾、保存人工修改，然后停止本机标注服务，再复制三个库。若仍存在非空`-wal`，不能只复制主文件；应先使用SQLite Online Backup API生成独立快照。迁移后只让服务器成为新的写入主库，避免本机和服务器各自标注后产生两份分叉。

原始SDF、NMRexp和大型训练数据不属于连续API标注的必需输入，现有峰表已在主库。若还要在服务器使用原始ShiftDB记录回溯、重新迁移等功能，另带 `data/nmrshiftdb2/nmrshiftdb2withsignals.sd` 和 `data/shiftdb_atom_identity_audit/source_seek_index.sqlite`，保持相对目录；部分旧来源路径是Windows路径，需要核对并调整。这些可选来源检查功能不等于迁移后自动可用。

### 从本机上传

把停机快照按三个原文件名放入同一迁移目录，例如 `E:\atomnmr_transfer\`，然后在项目目录的PowerShell执行（替换SSH用户名和地址）：

```powershell
ssh 你的SSH用户名@服务器地址 "mkdir -p ~/atomnmr_upload"
scp .\deploy\atomnmr-server-code-20261031.zip 你的SSH用户名@服务器地址:~/atomnmr_upload/
scp E:\atomnmr_transfer\assignments.sqlite E:\atomnmr_transfer\ai_annotations.sqlite E:\atomnmr_transfer\ai_benchmarks.sqlite 你的SSH用户名@服务器地址:~/atomnmr_upload/
```

之后下面的“实际上传路径”就是该SSH用户目录下的 `atomnmr_upload/`。首次传输主库约12.55GB，所需时间取决于实际上传带宽；上传完后校验SHA256，不以文件名相同当作上传完整。

## 3．有sudo时安装

下面以专用用户 `atomnmr`、目录 `/srv/atomnmr` 为例。首先上传代码ZIP和三个停机快照到SSH账户的临时目录，然后在服务器执行：

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-venv python3-pip unzip
python3 --version
sudo useradd --system --create-home --home-dir /srv/atomnmr atomnmr
sudo mkdir -p /srv/atomnmr/app /srv/atomnmr/data/databases /srv/atomnmr/secrets
sudo chown -R atomnmr:atomnmr /srv/atomnmr
sudo -u atomnmr unzip /实际上传路径/atomnmr-server-code-20261031.zip -d /srv/atomnmr/app
sudo install -o atomnmr -g atomnmr -m 600 /实际上传路径/assignments.sqlite /srv/atomnmr/data/databases/assignments.sqlite
sudo install -o atomnmr -g atomnmr -m 600 /实际上传路径/ai_annotations.sqlite /srv/atomnmr/data/databases/ai_annotations.sqlite
sudo install -o atomnmr -g atomnmr -m 600 /实际上传路径/ai_benchmarks.sqlite /srv/atomnmr/data/databases/ai_benchmarks.sqlite
sudo -u atomnmr python3 -m venv /srv/atomnmr/venv
sudo -u atomnmr /srv/atomnmr/venv/bin/python -m pip install --upgrade pip
sudo -u atomnmr /srv/atomnmr/venv/bin/python -m pip install -r /srv/atomnmr/app/deploy/server/requirements.txt
sudo -u atomnmr /srv/atomnmr/venv/bin/python -m pip freeze > installed-server-packages.txt
```

优先Python3.11/3.12。如果系统Python过旧，使用已有的Python3.12或conda环境代替，不要卸载服务器的系统Python。本服务不需要原项目用于BART训练的整套重依赖。

## 4．配置组内API和密钥

```bash
sudo install -o atomnmr -g atomnmr -m 600 /srv/atomnmr/app/deploy/server/api.example.json /srv/atomnmr/api.json
sudo install -o atomnmr -g atomnmr -m 600 /srv/atomnmr/app/deploy/server/atomnmr.env.example /srv/atomnmr/secrets/atomnmr.env
sudo -u atomnmr nano /srv/atomnmr/secrets/atomnmr.env
```

只在环境文件中把 `ATOMNMR_API_KEY` 改为真实组内密钥，不把密钥粘进命令行、代码仓库或聊天。环境文件供systemd读取，不会自动被普通Python启动加载。

API模板已按之前验证过的组内接口准备：

|项目|值|
|---|---|
|Base URL|`https://10.8.130.88/v1`，如果服务器上路由不同需修改|
|模型ID|`deepseek-v4.1-flash`，不是密钥显示名称|
|适配|`deepseek-local`|
|思考|关闭，避免此前复杂分子长时间没有最终答案|
|协议|`compact-v3`，JSON schema开启|
|上限|8192 token、600秒|
|并行|固定2并行起步，稳定后可从网页调整|
|CA|代码包内公开CA的Linux绝对路径，绑定指定服务器和指纹|

服务器模式使用 `EnvironmentManager`，不解密Windows保存的旧密钥。旧凭据和历史任务仍留在迁移库中，但服务器运行不使用它们。需要换密钥时修改私密环境文件并重启；服务器模式的网页密钥写入接口会明确拒绝。旧测试台若仍引用Windows凭据，查看历史正常，重新调用需另外适配服务器凭据；本入口主要用于正式持续标注。

## 5．后台运行和开机启动

```bash
sudo cp /srv/atomnmr/app/deploy/server/atomnmr.service /etc/systemd/system/atomnmr.service
sudo systemctl daemon-reload
sudo systemctl enable --now atomnmr
sudo systemctl status atomnmr --no-pager
curl --fail http://127.0.0.1:8767/api/health
sudo journalctl -u atomnmr -n 100 --no-pager
```

systemd按模板在进程失败时重启，重试有间隔和上限。日志使用journal，不无限追加一个应用文本日志。服务启动不会自动开始新批次，不会因为网页关闭而停止。

### 本机打开服务器网页

在本机PowerShell保持下面的SSH连接：

```powershell
ssh -L 18767:127.0.0.1:8767 你的SSH用户名@服务器地址
```

然后浏览器访问 `http://127.0.0.1:18767/auto.html`。隧道断开只影响网页访问，不停止服务器上的标注。此时不要误打开本机原来的8767端口页面。

## 6．第一次开始与中断恢复

Linux入口已经从api.json配置模型，网页“模型配置”沿用当前配置即可，不需要采用旧Windows端点（那些端点可能仍引用无法解密的Windows密钥）。网页中核对模型、固定并行2、处理范围，先查看少量真实结果的可用性，再继续长期运行。调用组内API不会自动适用官方DeepSeek的谷价策略。

开始持续任务后，在服务器执行下面命令查看任务完整ID：

```bash
curl --fail http://127.0.0.1:8767/api/auto/jobs
```

把要长期运行的任务ID填入私密环境文件的 `ATOMNMR_RESUME_JOB_ID=` 后面。不需要立即重启，下一次服务启动时会读取。只填实际的持续任务ID，不填测试批次或任意旧任务。

服务器入口启动时只恢复这个ID且状态为`interrupted`的任务；保持原任务模型和思考开关一致，同时把当前服务器的API地址、Linux证书路径和上限应用到后续请求，历史快照保留；若模型或思考开关不一致则拒绝自动恢复。`paused`、`attention`、`completed`保留状态，失败或结果未知的分子不自动重试。任务因正常停服变成paused后，需要从网页恢复；程序不能把用户主动暂停误当作故障。

**24小时在线和24小时永不暂停是两回事。** 当前任务可不设数量持续处理，但连续格式错误、限流、超时等仍会触发暂停保护。systemd只负责进程故障，不能修复模型输出错误。无人值守前应先评估组内连续输出是否稳定；若以后需要失败后继续下一分子、限流降并发、冷却恢复，应另做有上限的策略，不能靠无限重启反复提交未知请求。数据处理完也会正常结束，不会制造重复任务。

## 7．没有sudo时

可以把上述目录整体放到 `~/atomnmr/`，创建自己的venv，并把api.json中的CA路径改成真实绝对路径。用当前SSH用户运行，不创建专用系统账号。

```bash
cd ~/atomnmr/app
set -a
. ../secrets/atomnmr.env
set +a
nohup ../venv/bin/python -u -m annotation_tool_v3.server_linux --db ../data/databases/assignments.sqlite --config ../api.json --port 8767 > ../server.log 2>&1 &
```

这能脱离SSH会话运行，但不会自动开机启动，日志需轮转；不要重复执行造成多个进程。可用时优先使用`systemctl --user`；若服务器是Slurm等集群，不能把长期任务放在登录节点，应使用站点允许的作业或长期服务节点方式。

## 8．检查网络、证书与依赖

先运行健康检查确认程序环境；若API失败，检查服务器是否能路由到10.8.130.88、模型ID是否一致、NO_PROXY是否包含组内地址、公开CA路径/指纹是否正确。程序继续验证证书链与服务器身份，不使用`verify=False`。

`--check-api`仅查询`/models`，不分析分子；但这个启动入口会初始化任务恢复状态并占用端口，所以只能在服务停止时使用。需先按本节第7步加载环境文件再运行；不要对正在被其他服务使用的数据库同时运行诊断入口。端点不提供模型列表时，查询失败本身也不能证明chat接口不可用。

服务器上先安装并运行：

```bash
cd /srv/atomnmr/app
/srv/atomnmr/venv/bin/python -c "import rdkit,numpy,scipy,pyarrow,lmdb; from annotation_tool_v3.server_linux import EnvironmentManager; print('imports ok')"
```

这只是环境检查，不证明组内API性能或科学归属正确。

## 9．备份、回迁和日常维护

- 迁移验收前保留本机原库原样，核对三个快照的SHA256、关键表数量和几个手工标注分子。
- 运行中不要用上传操作覆盖正在使用的主库。升级代码前停服务并备份，数据库只保留一个写入主副本。
- 每天将三个库的一致性快照保存到另一块磁盘/异地存储。不要把活跃SQLite文件直接放网盘实时同步。
- 定期查看`/auto.html`的失败及一致性提示，不把“请求完成”当作“归属正确”。
- 停服：`sudo systemctl stop atomnmr`。查看日志：`sudo journalctl -u atomnmr -f`。升级后启动：`sudo systemctl start atomnmr`。
- 服务器新增标注应从服务器统一导出或停机回迁，不手动合并两台机器各自修改过的SQLite。

当前准备的是可部署代码及模板；只在本机验证了环境密钥入口、恢复规则与原有标注回归测试，尚未在真实Linux组内服务器安装或做24小时稳定性测试。

部署准备验证：本机37项服务器入口及原有AI标注相关测试通过。代码包133个文件，约541KB；已核对包含公开CA和词表规则，不包含SQLite、真实.env或Python缓存。该验证不能替代服务器上的Linux环境、网络及长时间运行验收。
